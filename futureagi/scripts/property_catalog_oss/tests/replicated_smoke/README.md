# Disposable replicated catalog diagnostics

**Plan-only until the parent confirms its standalone fixture is terminal,
cleaned, and headroom is available.** Nothing here changes the product, root
Compose file, production schema/admission policy, or an existing resource.
In particular, `c2854450c0d8` / `th7247-native-igazce` must remain untouched.

## Topology and resource budget

| Owned service | Image / process | Hard memory / swap ceiling | CPU cap |
| --- | --- | --- | --- |
| replica1 | `clickhouse/clickhouse-server:25.3-alpine` | 3 GiB / no additional swap | 2 |
| replica2 | same | 3 GiB / no additional swap | 2 |
| keeper | same image, independent `clickhouse keeper` process | 512 MiB / no additional swap | 0.5 |

Total container memory ceiling: **6.5 GiB**, below the 7 GiB allowance. Each
server also has a 2 GiB internal memory bound; diagnostic queries use 256 MiB
and one thread. Logs are rotated (two 5 MB files per container). Every service
has a PID limit. This is not Keeper HA, a three-replica qualification run, or a
disk-capacity stress test; disk volumes are disposable but not quota-enforced.

One independent Keeper, one fresh private bridge network and three fresh named data
volumes share a cryptographically random run label and ownership token. Two
distinct replica names use the **same** `/clickhouse/tables/<run-specific-db>/1/<table>`
paths. Four server HTTP/native ports and one Keeper port are allocated on
loopback only. Allocation is rechecked before startup; any port collision fails,
not a reassignment to another endpoint. The ACK-loss test uses one additional
ephemeral host-loopback listener, only for the duration of that request.
The network is not Docker `internal`: Docker Desktop suppresses published ports
on that mode. Runtime port mappings (not only configured bindings) are checked;
no external/shared network is attached. Packaged server cluster definitions are
replaced by the single fixture cluster.

`up` reads local Docker capacity and charges the full existing container caps,
the new 6.5 GiB cap and 2 GiB reserve. An uncapped existing workload or insufficient
capacity **blocks startup**; the runner never alters or stops it to gain room.
This conservative gate may require an explicit parent decision about scheduling.
No override is supplied. A local Unix-socket Docker context is mandatory.

## Schema and adapter scope

Both servers receive two run-specific `Atomic` databases:

- `property_catalog_dev_standalone_<run-id>`: the checked-in OSS table definitions.
- `property_catalog_dev_replicated_<run-id>`: the existing pinned production
  renderer's replicated definitions. Only the presentation `ON CLUSTER` clause
  is removed; each CREATE is sent explicitly to each owned server. Columns,
  sorting/partition keys, enum values, aggregate functions and `_version`
  parameters are retained and subsequently compared using the actual canonical
  schema verifier. This is fixture DDL, **not** the production installer.

| Canonical tables | Standalone engine | Replicated engine |
| --- | --- | --- |
| definition, delivery, activation-control events | MergeTree | ReplicatedMergeTree |
| attribute values | AggregatingMergeTree | ReplicatedAggregatingMergeTree |
| checkpoints, activations, source streams | ReplacingMergeTree(_version) | ReplicatedReplacingMergeTree(path, replica, _version) |

Inputs are the actual `025/026/027` catalog migrations, OSS control-event DDL
and `catalog_prod_schema.py` renderer. Source hashes and image ID/repository
digests are recorded. Changed product/schema inputs require a fresh plan before
live probes; cleanup remains possible without the product files staying frozen.

The read-only probe captures exact schemas, database engines, settings, grants,
`system.clusters`, all seven `system.replicas` entries on **each** server, and
the replica child names under every shared Keeper path. A self-contained `1/1`
entry, split Keeper paths, foreign replica, missing table or column/key drift
cannot count as the intended two-replica topology. Queue state is reported
separately from membership: 2/2 membership alone is not durability evidence.

It also invokes the actual read-only product functions:

- `catalog_prod_schema._prove_cluster`: the existing **three-replica** admission
  guard must reject this two-replica fixture; its exact exception is recorded.
  The production requirement is never patched to two.
- `verify_reader_activation_schema`: a local exact two-table schema check, not
  all-replica durability or control-event ordering admission.
- `inspect_installation`: records the returned identity or exact exception on
  each node before/during lag. It does **not** persist any identity file. Fresh
  identities generated by an empty-database inspection are not an installation.

The probes use generated XML users confined to these containers, library-only
settings and explicit owned loopback endpoints. They do not run Django apps,
load project `.env`, allocate a runtime identity, enable a reader, or activate a
catalog. The product grants/bootstrap policy is **not** weakened to admit the
fixture; the XML probe user's grants are evidence, not production grant proof.

## Commands

From the worktree root, use the existing backend venv so product adapter imports
are available (system Python can render plans if it supports the source syntax):

```sh
REPL_PY="$PWD/futureagi/.venv/bin/python"
REPL_RUNNER=futureagi/scripts/property_catalog_oss/tests/replicated_smoke/run.py

# No Docker calls; creates only private files inside replicated_smoke/runs/.
"$REPL_PY" -B "$REPL_RUNNER" plan

# Copy directory and run_id from the output. Do not run these until the parent
# explicitly releases headroom. These placeholders must be replaced literally.
"$REPL_PY" -B "$REPL_RUNNER" up RUN_DIRECTORY --confirm-headroom RUN_ID
"$REPL_PY" -B "$REPL_RUNNER" bootstrap RUN_DIRECTORY
"$REPL_PY" -B "$REPL_RUNNER" probe RUN_DIRECTORY
# Optional SELECT-only product proofs. Run admission on a fresh empty fixture,
# before scenarios insert diagnostic rows. It creates private local identity/
# admission files; it never enables a catalog or changes database data/grants.
"$REPL_PY" -B futureagi/scripts/property_catalog_oss/tests/replicated_smoke/keeper_probe.py RUN_DIRECTORY
"$REPL_PY" -B futureagi/scripts/property_catalog_oss/tests/replicated_smoke/admission_probe.py RUN_DIRECTORY
"$REPL_PY" -B "$REPL_RUNNER" scenarios RUN_DIRECTORY --confirm-faults RUN_ID
# Optional, separate actual Python adapter/profile diagnostic (no quorum claim).
"$REPL_PY" -B "$REPL_RUNNER" adapter-ack RUN_DIRECTORY --confirm-adapter-ack RUN_ID
"$REPL_PY" -B "$REPL_RUNNER" cleanup RUN_DIRECTORY

# Offline tests: fake transports/resources only, no Docker or real database.
"$REPL_PY" -B -m unittest discover \
  -s futureagi/scripts/property_catalog_oss/tests/replicated_smoke -p 'test_*.py' -v
```

The image must already be present; there is no implicit pull/build. Arrange a
public CH25.3 image pull separately if needed. No root Compose, `down`, `prune`,
image removal, external volume/network, or application `.env` is used.

## Deliberate failure scenarios and results

Each scenario persists an exclusive/fsynced intent containing the query ID,
complete synthetic reservation row, exact build-plan identity, body SHA-256 and
settings **before** one INSERT attempt. The actual build-plan model supplies all
ten stream declarations. These diagnostic reservations are not completed builds:
there are no fabricated checkpoints, delivery proofs, qualifications or activations.

1. **Lag without quorum:** stop fetches only for replica2's owned replicated
   `property_catalog_source_streams`; send one synchronous INSERT to replica1
   using `async_insert=0, wait_end_of_query=1` without adding quorum. Record the
   returned HTTP result and exact physical rows on both replicas.
2. **Lost HTTP ACK:** use a different identified reservation. A one-request
   loopback proxy forwards it once, records the upstream result, and closes
   before sending an HTTP status to the caller. The caller must retain
   `UnknownWrite`, never retry. Again record exact rows independently on both
   replicas while replica2 fetches are stopped.

Each phase records topology and local product-adapter outcomes during lag, then
restarts the same table's fetches in `finally`, runs a bounded sync, and rereads
both exact row identities. There is no automatic INSERT retry even after an
error, process death, or successful later read. An existing scenario/write intent
blocks another execution; create a fresh fixture after cleanup instead.

The report says `OBSERVED_MISSING_ALL_REPLICA_VISIBILITY` only when the specified
transport condition and exact replica1-present/replica2-absent evidence occurred.
Anything else is `NOT_REPRODUCED_OR_DIFFERENT_FAILURE`, with the actual observations.
Exit 2 signals schema/topology mismatch or a scenario/catchup not demonstrated;
exit 1 signals an execution error. Exit 0 means the requested diagnostic phase
completed—**never** that the product is production-admitted or fixed.

The row witness compares the complete canonical row, not count equality alone.
Even eventual identical rows prove visibility only: not crash/power-loss fsync,
atomic multi-table ClickHouse commits, Kafka acknowledgment behavior, or safe
all-replica activation. The HTTP fault client mirrors the Go sink's explicit
synchronous settings; it is not execution of the actual Go consumer binary.

The optional `adapter-ack` phase creates one new fixture-only SQL user on replica1
with the exact existing OSS control-writer grants, scoped to this run's standalone
database. Its server profile inherits `async_insert=1, wait_for_async_insert=0`
and a 60-second non-adaptive async flush delay. The actual `NativeCatalogClient`
and `_ActivationControlClient` each INSERT one row once. Immediate full-row reads
and server `system.query_log` must show two exact token-bound `QueryFinish` events
with `async_insert=0`, one written row, and no exception. It captures product source
hashes before/after; missing or different evidence returns failure, not a claimed
pass. The control row is a synthetic DISABLE serialization fixture, not a qualified
activation. No reader is bound and no lifecycle build is activated.

## Cleanup and remaining gates

The separate `admission_probe.py` uses the actual Python admission producer,
the actual native and HTTP clients with exact owned NAT mappings, the pinned
schema verifier and live Keeper membership proof. Each family is independently
proven empty before private fixture identity initialization. It verifies both
standalone (one node) and replicated (two nodes), then reattests and reuses each
immutable descriptor. An existing local probe directory refuses rerun rather
than overwriting evidence. It does not change grants or prove production roles,
write completion, Kafka delivery, or activation. The production three-member
requirement is not weakened to fit this diagnostic fixture.

Cleanup validates every exact planned resource name, run/token/Compose labels,
and then rechecks identity/ownership before deletion. It removes only those
container IDs, exact volume names and network ID. Foreign or protected resources
cause refusal before deletion; there is no label-wildcard cleanup. Manifest and
evidence files remain. Run directories are 0700, manifests/evidence 0600, and
read-only container XML 0644 inside the private directory. Manifest loading
rejects final symlinks, FIFOs, noncanonical data, writable/tampered configs and
oversized files. Cleanup does not recursively delete host directories.

Still open: quorum on data/ledger/control writes; read ordering across lagging
replicas before choosing/advancing control heads; cluster-wide installation
identity/topology/grants admission; actual Go consumer/image integration;
three-replica production qualification; Keeper HA; crash/power-loss durability.
A standalone run alone cannot demonstrate replicated correctness.
