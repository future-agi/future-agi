STEP 01 / 27PROPOSED · SYNTHETIC EXAMPLE

Receive spans

SDK / exporter → collector

Illustrative decoded span batch. Existing OTLP wire encoding and authentication remain in the ingestion adapter. The collector derives tenant scope from authentication.

Input / request

{
  "organization_id": "org_1",
  "workspace_id": "ws_1",
  "project_id": "project_7",
  "trace_id": "trace_17",
  "spans": [
    {
      "span_id": "span_root",
      "parent_span_id": null,
      "input": {
        "request": "Refund exactly USD 100 for order O-42."
      },
      "output": {
        "message": "Refunded USD 100."
      },
      "end_time": "2026-09-11T10:00:00Z"
    },
    {
      "span_id": "span_refund",
      "parent_span_id": "span_root",
      "input": {
        "tool": "refund",
        "order_id": "O-42",
        "amount": 10,
        "currency": "USD"
      },
      "output": {
        "refund_id": "R-9",
        "status": "posted",
        "amount": 10,
        "currency": "USD"
      },
      "end_time": "2026-09-11T09:59:59Z"
    }
  ]
}

Output / response

{
  "http_status": 200,
  "meaning": "accepted by collector; not a whole-trace completion receipt"
}

Where it goes / what persists

Collector buffers span rows; batches may mix traces and arrive out of order.

If this fails or changes

Rejected auth/invalid scope fails ingestion. HTTP acceptance alone must not trigger a stored-trace notification.

STEP 02 / 27PROPOSED · SYNTHETIC EXAMPLE

Store the batch

Collector → ClickHouse

Flush by batch size or timer; publish only after the storage boundary is satisfied.

Input / request

{
  "operation": "insert_spans",
  "organization_id": "org_1",
  "workspace_id": "ws_1",
  "project_id": "project_7",
  "trace_id": "trace_17",
  "span_ids": [
    "span_root",
    "span_refund"
  ],
  "write_mode": "synchronous"
}

Output / response

{
  "http_status": 200,
  "stored_batch": "batch_801",
  "root_spans_in_batch": [
    "span_root"
  ]
}

Where it goes / what persists

Canonical spans stay in ClickHouse. This receipt covers this batch only.

If this fails or changes

Failed inserts do not emit a stored-root event. Current optional async_insert with wait_for_async_insert=0 needs a visibility-aware change or disabling for this path.

STEP 03 / 27PROPOSED · SYNTHETIC EXAMPLE

Announce a stored root

Collector → Kafka

Proposed dedicated topic on the existing broker. This first design emits after ended root spans are stored; no per-span quiet timer is required. Split batches by count and encoded bytes.

Input / request

{
  "topic": "error-feed.trace-available.v1",
  "key": "org_1/ws_1/project_7",
  "value": {
    "version": 1,
    "event_id": "event_901",
    "organization_id": "org_1",
    "workspace_id": "ws_1",
    "project_id": "project_7",
    "event_kind": "root_span_written",
    "traces": [
      {
        "trace_id": "trace_17",
        "root_span_id": "span_root",
        "root_end_time": "2026-09-11T10:00:00Z"
      }
    ],
    "emitted_at": "2026-09-11T10:00:02Z"
  }
}

Output / response

{
  "topic": "error-feed.trace-available.v1",
  "partition": 3,
  "offset": 108,
  "broker_acknowledged": true
}

Where it goes / what persists

The event carries IDs, never full trace bodies. event_id remains stable across retries of this emission; later emissions get new IDs.

If this fails or changes

Bound the producer queue/deadline. A CH write followed by publication failure leaves a notification gap recovered by step 27. Existing property-catalog messages are not this schema.

STEP 04 / 27PROPOSED · SYNTHETIC EXAMPLE

Persist incoming work

Node Kafka consumer → Django control operation → Postgres

Consume short batches. In one DB transaction, deduplicate transport deliveries and record pending work. This logical operation is proposed; it is not an existing HTTP route.

Input / request

{
  "operation": "record_trace_notifications",
  "deliveries": [
    {
      "topic": "error-feed.trace-available.v1",
      "partition": 3,
      "offset": 108,
      "value": {
        "version": 1,
        "event_id": "event_901",
        "organization_id": "org_1",
        "workspace_id": "ws_1",
        "project_id": "project_7",
        "event_kind": "root_span_written",
        "traces": [
          {
            "trace_id": "trace_17",
            "root_span_id": "span_root",
            "root_end_time": "2026-09-11T10:00:00Z"
          }
        ],
        "emitted_at": "2026-09-11T10:00:02Z"
      }
    }
  ]
}

Output / response

{
  "accepted_events": 1,
  "duplicate_events": 0,
  "pending": [
    {
      "organization_id": "org_1",
      "workspace_id": "ws_1",
      "project_id": "project_7",
      "trace_id": "trace_17",
      "job_id": "job_17",
      "generation": 1,
      "state": "waiting",
      "not_before": "2026-09-11T10:01:02Z"
    }
  ]
}

Where it goes / what persists

Durable pending IDs and due times survive Node restart. DB receipt time anchors the example 60-second delay. Pending IDs are retained while needed, not an everlasting row per incoming span.

If this fails or changes

If DB persistence fails, leave offset uncommitted. At sustained scale, batch/coalesce writes and measure pending-state storage; bounded overflow must mark the project for reconciliation.

STEP 05 / 27PROPOSED · SYNTHETIC EXAMPLE

Acknowledge delivery

Node consumer → Kafka

Commit only the contiguous offsets whose pending work has been durably recorded. The committed offset is the next record to read.

Input / request

{
  "operation": "commit_offsets",
  "consumer_group": "error-feed-discovery-v1",
  "offsets": [
    {
      "topic": "error-feed.trace-available.v1",
      "partition": 3,
      "next_offset": 109
    }
  ]
}

Output / response

{
  "committed": true
}

Where it goes / what persists

The broker no longer needs to redeliver this record. Omega has not started yet.

If this fails or changes

Crash between step 04 and 05 causes harmless replay through the durable inbox. Never commit past a failed earlier record in the partition.

STEP 06 / 27PROPOSED · SYNTHETIC EXAMPLE

Wait and select due work

Scheduled Node coordinator → Django control operation

A short periodic tick claims eligible work. not_before replaces an in-memory sleep per trace. Apply project enablement, fair quotas and the explicit admission policy.

Input / request

{
  "operation": "claim_due_investigations",
  "worker_id": "node_2",
  "engine_version": "ef-v2-doc-example",
  "now": "2026-09-11T10:01:03Z",
  "limit": 5
}

Output / response

{
  "claims": [
    {
      "organization_id": "org_1",
      "workspace_id": "ws_1",
      "project_id": "project_7",
      "job_id": "job_17",
      "trace_id": "trace_17",
      "generation": 1,
      "attempt_id": "attempt_1",
      "lease_token": "lease_17_v1",
      "lease_expires_at": "2026-09-11T10:03:03Z",
      "selection": {
        "policy": "all_eligible",
        "reason": "root_available"

Where it goes / what persists

A unique active claim prevents concurrent duplicate work. All eligible traces are selected in this walkthrough. Sampling/representative selection is a separately configured policy, not silently added here.

If this fails or changes

No due work returns claims:[]. Capacity exhaustion defers visibly. Claims must filter engine compatibility and reserve shared org/project/provider capacity atomically.

STEP 12 / 27PROPOSED · SYNTHETIC EXAMPLE

Spawn a focused child

Omega controller → child agent → model API

The controller chooses the question and task-specific prompt; host supplies immutable rules, tools and budget. No static failure taxonomy is introduced.

Input / request

{
  "tool": "spawn_investigator",
  "arguments": {
    "child_id": "child_1",
    "question": "Was the requested amount actually refunded, and is recovery recorded?",
    "task_prompt": "Inspect the refund call and receipt. Compare currency, amount and order ID to the original request. Check subsequent evidence for correction. Report citations and missing facts.",
    "allowed_tools": [
      "read_span",
      "list_children",
      "search_trace"
    ],
    "max_calls": 3
  }
}

Output / response

{
  "child_id": "child_1",
  "state": "running",
  "shared_workspace": "/work/attempt_1/",
  "reserved_call_budget": 3
}

Where it goes / what persists

At most two depth-one children in this example. Spawning is adaptive; simple cases can need none. Concurrency and call reservations are enforced by the host.

If this fails or changes

Budget exhausted returns a typed refusal to spawn; the controller must finish with what is supported. Children cannot recursively delegate.

What this plan commits to—and what still needs evidence

What changed

Kafka carries ended-root notifications. Node handles the delayed scheduled jobs. Temporal is absent from this proposal.

What “ready” means

Root ended + fixed delay. This is a scan-readiness heuristic. Late child spans can still arrive; this first version does not track every child notification.

Where the full trace goes

ClickHouse → streamed attempt files. Exact fields stay accessible through indexed reads. Model context still has a finite budget.

What clustering does

Atharva receives supported occurrences and returns issue assignments. Django persists membership. Clustering does not rewrite trace outcomes.

What is not built by this document

New Kafka topic/message, durable Node job boundary, streaming file tools, publication adapters and governed learning integration require implementation and tests.

What needs measurement

Arrival rate and bursts, selected fraction, model cost, file-read recall, late-span delay, DB read load and pending-work storage.

Clustering is a black box with a reviewable boundary.Steps 18–20 show occurrence payloads, registry context, attach/create/unassigned output, version checks and persistence. Atharva can replace the internals and confirm the contract. Grouping never silently changes a trace-level finding.

At 30 million traces/day, 60 seconds per investigation and 100% admission, average concurrency would be about 20,833 investigations. At 1% it would be about 208. These are illustrative calculations, not measured capacity or an approved sampling policy. Queue choice does not reduce model cost.

Provider errors, unknown outcomes and unselected traffic remain distinct. A completed report can be republished without rerunning Omega. A crash before the report is durably accepted can lose that result; the attempt is recorded as interrupted. See step 26 and the downloadable plan.
