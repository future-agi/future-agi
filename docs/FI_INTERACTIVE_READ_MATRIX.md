### Deployment and synchronization state

The catalog owns exactly six isolated ClickHouse tables:
`property_definition_catalog`, `span_attribute_value_catalog`,
`property_catalog_checkpoints`, `property_catalog_activations`,
`property_catalog_deliveries`, and `property_catalog_source_streams`. The first
is the only definition catalog, the second contains observed span-attribute
values, and the remaining four are control-plane ledgers. No canonical source
table is changed.

The DEV runtime is one organization/workspace per Python/Go sidecar and shared
durable volume. Exactly one default-off Temporal schedule runs every 120
seconds on `property_catalog_dev_sidecar` with overlap skipped. Its durable
AUTO lifecycle performs incremental reconciliation normally and selects a full
repair when the lineage anchor reaches 24 hours or 2,048 active revisions.
Initial backfill remains an explicit operator action; there is no second daily
schedule. Additional workspaces require independent sidecars, queues, and
volumes.

The reviewed DEV rollout requires its canonical spans source database and
isolated catalog target database to differ. Before it constructs a target
client, inspects schema, reads source spans, acquires a lease, or writes, it
proves the exact allowlisted project set in one read-only repeatable-read
PostgreSQL snapshot through `public.tracer_project` and
`public.accounts_workspace`. Missing or duplicate projects and any project or
workspace organization mismatch fail closed. Ownership is revalidated inside
the revision snapshot and immediately before source, relational, publish,
fence, and activation boundaries, with an immutable authorization/execution
proof binding the reviewed request. Soft-deleted projects may participate only
for tombstone repair and must pass the same ownership proof.

The 2026-08-19 local rerun includes 306 property-catalog/dataset-limit tests and
802 trace-filter/graph/deadline tests. The annotation/bulk matrix completed 295
tests with ten explicit ClickHouse integration skips; thirteen dataset-add
integration cases were blocked before test execution because the isolated local
ClickHouse service was unavailable. Earlier current-tree gates also include the
114-test offline qualifier suite. The Go property catalog package passes under
the race detector and `go vet`. The
current `0817j` all-DEV evidence records 90 active workspaces, a 263-project
owned inventory, 89,894 physical definition rows, and 2,151,977 physical value
rows. Interactive Kartik DEV coverage includes Observe Trace/Span
property/value search and pagination, Primary Graph, Eval Settings, annotation
automation, dashboard/widget pickers, dataset selection, and both simulation
selectors. The latest picker regression pass is 135/135. The named
dense/sparse/voice production scale matrix remains pending. The DEV Kafka
ledger contains 91 committed, gap-free terminal deliveries across the 90
workspaces, but they are zero-data drain boundaries and are not claimed as a
non-empty fresh-ingestion smoke. Non-empty hot ingestion remains covered by
the collector/runtime tests because canonical DEV source writes were not
authorized. No account data was copied locally or to production.

Exact graph preparation is deployed on a dedicated additive
`exact_aggregation` Temporal worker from the matching core/EE stack. The prior
shared `tasks_xl` worker did not register
`tracer.refresh_exact_aggregation_snapshot`, which caused the observed pending
graph and dashboard error states. A fresh filtered graph completed the activity
successfully; individual ClickHouse SELECTs took 4.12–49.84 ms and the full
activity took about 0.3 seconds. The existing shared worker and database were
not changed.

The final current-tree integration pass additionally covers 200 request-wall
and error-boundary tests, 166 bounded experiment/simulation/eval-task/
automation/AI-filter backend tests, 153 active frontend read-consumer tests,
and 112 generated contract tests. Project, automation-rule, eval-metric,
eval-task detail/log, experiment-row, and dataset-point consumers now use one
env-configured visible-action wall, preserve the last valid payload, reject
malformed success shapes, and expose explicit Retry. The Charts action
now uses runtime query validation and a shaped three-branch graph response
contract under an outer 9.5-second wall. These local results do not promote the
14 changed eval-task, automation, and simulation mutation operations into the
interactive-read SLA; those require mutation-specific idempotency or async
acceptance evidence.

The current-source SELECT-only qualifier covers nine explicit telemetry windows:
**30m, 1h, 6h, 24h, 7d, 30d, 90d, 180d, and 365d**. It rediscovers
authorized targets at run time, exercises dense Whatfix and sparse
Colektia/Colly profiles, and runs observed-value eval, annotation, and F7
profiles on applicable trace/span/session/voice list routes. It permits an
exact empty result in genuinely empty short windows and requires positive
long-horizon population evidence before a named profile can qualify. The six
source-bound shards (`whatfix`, `colektia`, `mudflap`, `trace_system`,
`whatfix_graphs`, and `colektia_graphs`) run sequentially under independent
600-callback fuses; their exact worst cases are 564, 564, 284, 544, 480, and 452
callbacks. Trace, span, session, and root dashboard queries cover all 11 filter
profiles across all nine windows with refresh disabled on both the Whatfix dense
and Colektia sparse targets (396 lanes each; 792 total). Date-only Observe reads
may use the approved rollup; filtered Observe reads must be exact and bind their
public canonical filter digest/count and exact UTC window to the executed query
or cache identity. Every dashboard lane must return a complete exact worker
series for the requested UTC window. Users graph remains excluded from the
SELECT-only route set. The exact
dataset route and metrics catalog share one boundedly selected dataset/column
representative; metrics must include and UUID-search its `dataset_column`

current-source production route-matrix result exists. An earlier source-bound
US result failed named-target rediscovery before API execution; a later isolated

callbacks. The fresh `0816d` plan remains pending read-only remote-state

The requested time presets are:

| ID  | Public meaning  |
| --- | --------------- |
| W0  | Recent (1 hour) |
| W1  | Today           |
| W2  | 7 days          |
| W3  | 30 days         |
| W4  | 3 months        |
| W5  | 6 months        |
| W6  | 12 months       |

Filter columns use these symbols:

| Symbol | Meaning                                                                                                     |
| ------ | ----------------------------------------------------------------------------------------------------------- |
| `Y`    | Public contract and focused parity tests cover the shape. This does not by itself prove production latency. |
| `C`    | The public contract/compiler accepts the shape, but representative scale is not release-qualified.          |
| `N`    | The endpoint is a catalog, identity read, or other surface where that row-filter shape is not applicable.   |
| `U`    | Unsupported, pre-existing unbounded behavior, or insufficient evidence; no green claim.                     |

The canonical filter IDs are `F0` (date/project only), `F1`
(system/status), `F2` (sparse typed attribute), `F3` (dense typed attribute),
`F4` (system + attribute), `F5-E` (the PROPERTY matrix's F5 evaluation cell),
`F6-A` (the PROPERTY matrix's F6 annotation/annotator cell), and `F7`
(attribute + evaluation + annotation conjunction). The compact tables below
retain one `F2/F3` column because their public shape is shared; they omit a
separate F7 column because no historical endpoint-scale F7 result exists.
The current qualifier schedules F7 for row-list routes and for all three
Observe graph kinds on both Whatfix and Colektia, but F7 remains pending live evidence rather
than inheriting green status from its component filters. Dashboard F7 remains
outside the qualifier. Date ranges for tracing lists and graphs are
encoded in the shared `created_at` or `start_time` filters; they are not
separate `period` parameters.

### Export compatibility note

The material public contract change in this section is CSV scope. The same four
download URLs and CSV media type remain, but a synchronous download now means
one bounded, explicitly classified page rather than every matching retained
row: trace is capped at 100 rows; span, session, and Users are capped at 20.
Callers that assumed a complete all-row file must refine filters or move to a
future asynchronous export workflow. A sorted Users export is rejected with a
typed `422` because cursor ordering cannot preserve that sort.

For conversation/voice projects, trace export first uses the configured voice
agent signal and then a bounded compatibility probe for provider-only projects.
It routes the selected bounded page through `list_voice_calls`, projects it onto
the historical voice CSV headers, and names the file `*_voice_calls.csv`.
`attribute_keys` can request additional columns, while discovered eval names are
projected into stable output/reason pairs. The dedicated compatibility contract
is covered by
`test_voice_trace_export_preserves_legacy_schema_on_one_bounded_page`.
What changed is completeness, not the voice schema: the CSV contains one
bounded page and truthfully appends a truncation marker when more matching rows
remain. The retained historical runtime smoke exercised a generic trace export,
so it is not itself live evidence for the voice branch; the successor qualifier
contains a distinct bounded voice-export lane that is still pending. See
[trace.py](../futureagi/tracer/views/trace.py) `TraceView.get_trace_export_data`,
`TraceView.list_voice_calls`, and `_voice_call_export_projection`;
[trace.py serializer](../futureagi/tracer/serializers/trace.py)
`TraceExportQuerySerializer`; [bounded_csv.py](../futureagi/tracer/utils/bounded_csv.py);
and [test_bounded_page_exports.py](../futureagi/tracer/tests/test_bounded_page_exports.py).

### Users response honesty

The default Users cursor is ordered by a bounded `span_user_rollup` candidate
population with a compact live `end_users` fallback, then exact finite replay
of touched identities. It therefore returns `query_exact: false`,
`ordering_exact: false`, and
`query_provenance: span_user_rollup_end_users_candidate`. Presentation
`num_sessions` counts the latest live raw session IDs and is explicitly marked
with `num_sessions_is_approximate` and `approximate_fields: ["num_sessions"]`;
the frontend renders `~N` with a tooltip. A session-count filter continues down
the exact remap-aware predicate path rather than filtering the approximate
presentation value. The supporting contract is
[trace.py serializers](../futureagi/tracer/serializers/trace.py)
`UsersTableRowSerializer` / `UsersResultSerializer`, with frontend behavior in
[sessionCountHonesty.js](../frontend/src/sections/projects/UsersView/sessionCountHonesty.js).

### Graph corrections found by runtime qualification

- Session and Users exact graph SQL previously exposed a ClickHouse scalar-array
  alias on the right side of `IN` inside `PREWHERE`. The corrected source builds
  the finite physical-ID candidates as a relational CTE and uses
  `IN (SELECT candidate_id FROM candidate_relation)`. This is a SQL-validity
  correction, not a sampling shortcut.
- ClickHouse returns `toStartOfMonth` as a Python `date` with the production
  native-client settings. The trace metric reducer previously accepted only
  `datetime`, so the Whatfix W6 `has_eval` graph failed after its database work
  had succeeded. It now accepts `date` or `datetime`, normalizes both through
  `BaseQueryBuilder._normalize_timestamp`, and continues to reject strings and
  nulls as schema drift.
- A W6 annotator trace graph then showed that the finite, at-most-five-trace
  relation classifier could legitimately need more than its old 750ms
  statement slice for a candidate-scoped `Score FINAL` read. Its statement cap
  is now 1.5 seconds, still clamped by the shared 9.5-second request wall; a
  failed batch remains atomic and becomes a sanitized retryable error rather
  than a published prefix.
- Exact trace/span graph execution no longer gives sequential subqueries
  independent 30-second grants. Anchor, witness, classifier, contribution,
  partition, and PostgreSQL annotation reads share one action-owned 9.5-second
  wall and receive a monotonically shrinking, millisecond-round-down budget.
  Exhaustion remains a typed exact-read failure, so a partial graph is never
  formatted or published.

## Read policy and frontend continuation invariants

- All six Observe/prototype list actions start one 9.5-second wall before
  request validation and tenant/project PostgreSQL reads. PostgreSQL statements
  receive shrinking transaction-local timeouts, and ClickHouse, enrichment,
  continuation construction, and response publication consume only the same
  remaining budget. The trace/span/session graph actions and the three user
  graph actions use that same rule across scope/config PostgreSQL reads and
  graph work. Deadline/database failure is a sanitized `503`, never a late
  successful response. This leaves transport headroom below the requested
  ten-second SLA.
  Exact trace/span graph anchor, witness, classifier, contribution, partition,
  and annotation reads consume one cumulative action wall rather than receiving
  independent grants; each phase gets only the shrinking remainder.
  The pageable dashboard **system** filter-value action starts a stricter
  request-owned four-second wall before project/cursor preparation; lower-level
  attribute readers retain their 8-second ceiling but receive only the
  remaining public deadline when one is supplied. Users list/export uses one
  8-second wall, and eval-list charts use two seconds. Each sequential phase
  receives only the remaining wall time.
- Eval-log table count/page/hydration uses one 8.5-second read-only PostgreSQL
  snapshot, with a 9.5-second browser abort wall. Alert preview/saved graphs use
  one 8.5-second backend wall (one-second metadata cap and six-second ClickHouse
  cap) plus a separately configured browser abort wall. Both surfaces fail visibly, preserve
  already rendered data, and expose explicit Retry; they do not convert failure
  into an empty success.
- Charts query validation, project/eval scope reads, graph dispatch, and
  response publication are fenced by one outer 9.5-second action deadline. Its
  checked Swagger response explicitly models single system-metric,
  all-system-metrics, and eval-series result branches instead of an unshaped
  object. The active Charts consumer uses one configured abort/retry state.
- Project lists, automation-rule pages, eval metrics, eval-task detail/logs,
  experiment row blocks/details, and both dataset-point drawers use one
  configured frontend action wall. A failure retains prior data and remains
  visible; dataset adjacency plus cell hydration share the same signal rather
  than receiving independent budgets.
- The active frontend dashboard filter-value picker timeout is 4.8 seconds. It is an
  HTTP fail-safe, not extra database time, and its abort signal is carried to
  every physical cursor-page request.
- Interactive ClickHouse statements use finite memory, byte, result, thread,
  query-count, payload, and process-concurrency controls. CATALOG does not use
  an application `max_rows_to_read` source-row ceiling on these paths.
- A bounded pause is not exhaustion. Observe trace/span/session/voice/Users and
  attribute-value frontend flows preserve already published rows, reject
  repeated or non-advancing cursors, carry a real abort signal, and expose
  Continue/Load more when the server publishes an advancing checkpoint.
- Numbered compatibility pages can return typed `422 page_depth_exceeded` when
  the requested ordered prefix cannot be proven inside the finite protocol.
  Retryable database/budget failures are `503`; they are never converted into
  a successful empty list.
- Exact aggregate APIs may return `pending` while a background worker computes
  a snapshot. The frontend retains the last exact snapshot and does not render
  pending empty arrays as a completed zero graph.
- The merged eval-score schema/backfill work is operationally separate from
  these reads. The SELECT-only qualifier starts with
  `NO_STARTUP_DB_MUTATIONS=true` and `STARTUP_DB_MUTATION_MODE=disabled` and
  must never invoke `backfill_eval_score`; historical index materialization is
  a separately authorized deployment mutation.
